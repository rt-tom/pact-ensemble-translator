## Context

После перевода, редактора, аудита и repair букран вызывает resolve_format_mappings, затем run_formatting_align детерминированно вставляет inline-теги. Модель уже получает только PID с inline_spans, но планировщик использует порог 80 фрагментов для одного вызова и иначе делит по 12 PID. Локальный сервер форматтера получает эффективный бюджет reviewer-роли: для qwen38 это reasoning 8192. В исследованном прогоне resolve_format_mappings не получил role_policy и использовал малый старый потолок ответа.

Архивный formatting-reasoning-fix уже предполагал один вызов и reasoning=0. Действующее требование local-model-registry задаёт для каждой роли бюджет «база модели + добавка роли». Новый OpenSpec явно вводит исключение для formatting; остальные роли остаются аддитивными.

## Goals

- Один запрос на все размеченные PID, если он помещается; иначе минимальное число безопасных запросов.
- Нулевой reasoning для технической задачи привязки тегов.
- Полный проверенный mapping без изменения русских слов.
- Сохранение диагностики и текущего контракта отчёта/debt.

## Decisions

### D1. Компактный вход по размеченным PID

На каждый PID с inline_spans формируется одна структура: pid, английский исходник один раз, список span_id/tag/source_text и соответствующий финальный русский перевод один раз. PID без тегов не передаются. Английский контекст сохраняется для многозначных слов; повторяющуюся XML-обвязку и экранирование JSON внутри XML заменяет структурированный вход. Ответ остаётся списком pid, span_id, target_text, occurrence. Модель не редактирует перевод.

### D2. Планирование по реальному бюджету

Сначала планируется один вызов для всего списка размеченных PID. Для локальной модели учитываются разрешённое окно контекста, размер сериализованного промпта, потолок ответа по политике роли и запас. Если всё помещается, выполняется ровно один вызов независимо от числа PID и тегов. Иначе последовательные PID упаковываются в минимальное число групп, помещающихся в бюджет. Для удалённой модели без известного окна пробуется один запрос в рамках её политики; деление происходит при явной ошибке контекста или длины. Причина деления и размеры групп пишутся в диагностике. Пороги 80 span и 12 PID перестают управлять production-путём.

### D3. Одна политика вызова

Букран один раз разрешает formatting RoleCallPolicy и явно передаёт её форматтеру и backend adapter. Sampling и max_output_tokens берутся только оттуда. Если политика отсутствует, этап пишет диагностированный debt и не делает модельный вызов с маленьким fallback. Глава сохраняет мягкий исход. Для каждой планируемой группы ответу выделяется место в пределах общего потолка роли; finish_reason=length обрабатывается по D5. Потолки других ролей не меняются.

### D4. Явный reasoning=0 для formatting

В role_budgets добавляется валидируемое поле reasoning_budget_override, разрешённое только для formatting со значением 0. При вычислении локального бюджета это значение имеет приоритет над формулой «база модели + добавка роли». Router, аргументы запуска и provenance свежего вызова обязаны показывать 0; при переходе между formatting и audit/entity_extractor сервер перезапускается с нужным бюджетом. Профиль qwen38 и бюджеты всех остальных ролей сохраняются. Удалённый форматтер продолжает вызывать модель без reasoning effort (или с явным none, если этого требует транспорт). Одного enable_thinking: false для локального сервера недостаточно.

### D5. Восстановление с уменьшением объёма работы

Валидный JSON может содержать не все привязки. Каждая привязка проходит полную проверку: допустимые pid/span_id, непустая подстрока внутри своего русского PID, корректный occurrence, отсутствие наложения и допустимый тег. Валидные привязки сохраняются; повторный запрос содержит только неразрешённые фрагменты и нужный контекст PID. При обрезании по длине/контексту или полностью невалидном JSON делится только неудачная группа, без идентичного повтора с тем же лимитом. Для временной транспортной ошибки разрешён один ограниченный повтор с задержкой. Число вызовов и глубина деления ограничены; оставшиеся фрагменты становятся FormattingIncident debt. Теги не угадываются.

### D6. Артефакты и resume

Формы translations.json и formatting_report.json сохраняются; raw/messages/meta каждой попытки остаются в выходной папке главы. Старые имена formatting_batchN_* можно оставить для совместимости, даже если обычно N=1; в meta добавляется причина деления/повтора. При нулевом бюджете reasoning-файл может быть пустым, и отчёт не должен утверждать, что reasoning стримился. FORMATTING_POLICY_VERSION повышается, чтобы отличать новые результаты. Завершённые старые главы не переписываются при обычном resume; новая политика применяется к свежему этапу или явно принудительному повтору. Сервер форматтера по-прежнему живёт в пределах одной главы, а логи лежат в chapter out_dir/server_logs.

## Risks and checks

- Нулевой reasoning может ухудшить выбор русской подстроки. Нужны тесты многозначных слов, склонений, повторяющихся подстрок и нескольких тегов на PID, со сравнением числа валидных привязок и debt со старым путём.
- Большой ответ может оборваться или не поместиться. Планирование и деление по D5 ограничивают потерю, исходный русский текст сохраняется.
- Исключение из локальной формулы меняет маршрутизацию. Тестируются фактические launch args, переходы между reviewer-ролями, provenance и закрытие сервера при ошибке.
- Отсутствие role_policy больше не ведёт к скрытым вызовам с 900–1180 токенами: тест проверяет диагностированный debt.
- Исходный текст, переводы, промпты и артефакты прогона не передаются внешним сервисам для проверки. OpenSpec не предусматривает запуск production-пайплайна.

## Rollout

Реализация и независимое ревью проходят в изолированном worktree на media. Затем выполняются целевые unit/integration-тесты и проверка OpenSpec. Merge, deployment и любой живой прогон требуют отдельных решений владельца. Откат — возврат к прежнему коду и конфигурации; старые отчёты и переводы остаются читаемыми.
