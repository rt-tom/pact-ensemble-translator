## 2. Причины (с кодом)

### 2.1 Re-audit переаудирует ЦЕЛЫЕ chunk'и, а не изменённые PID

Место: `pact_v4/phase4/repair.py:1121-1274` (`_reaudit_chunks`), вызывается из:

- `pact_v4/phase4/repair.py:1903` (после round 1, scope = changed + соседи);
- `pact_v4/phase4/repair.py:2015` (после round 2, scope = changed + соседи);
- `pact_v4/pipeline/v4_phase12_strict_runner.py:1736` (quarantined-retry, scope = retry-chunks).

Механика: для каждого chunk из scope прогоняются ВСЕ его PID через qwen_chapter_audit и
gemma_russian_review (`for detector: for chunk_id:` — цикл на строке 1219-1223).
Scope расширяется соседями (`_neighbour_chunk_ids`, repair.py:1104-1118: ±1 chunk),
при 16 изменённых chunk'ах соседи перекрывают почти все → scope ≈ все 16.

Итог: **~103 из 269 вызовов — повторная аудиторская проверка практически неизменённого текста.**

### 2.2 Repair вызывает модель ПО РЕГИОНУ, не по chunk

Место: `pact_v4/phase4/repair.py:757-820` (`_apply_region_edit`) — один `repair_caller(...)`
на каждый plan/регион (вызов на строке 795). B12 забатчил только re-gate
(`region_fidelity_gate.batch`, repair.py:879-923), но не сам ремонт.

Итог: 73 региона = 75 вызовов `phase4/region_repair`.

### 2.3 Re-audit раунды повторяются без детекта «нет прогресса»

Место: `pact_v4/phase4/repair.py:1959` (`if max_rounds >= 2 and (blocking_findings or boundary_changed)`)
и `pact_v4/phase4/repair.py:1896-1914` (re-audit после round 1) — re-audit прогоняется
полностью после каждого раунда, даже если findings между раундами не изменились
(нет сравнения набора findings до/после, нет раннего выхода по сходимости).
Плюс quarantined-retry (runner:1736) добавляет третий полный re-audit.

## 3. Предложения

### 3.1 Re-audit только изменённых PID (+ узкий контекст)

- Суть: re-audit должен получать не `chunk_ids`, а **`target_pids`** (PID изменённых
  регионов + дискурсивные соседи по PID в пределах chunk), и прогонять модель только
  по ним. Детерминированный слой (`_reaudit_chunks` 1152-1215) — уже per-PID, оставить.
- Оценка экономии: ~70–90 вызовов/главу (38% → ~10%).
- Риски: (а) qwen/gemma аудит по chunk'у может опираться на контекст всего chunk —
  нужен узкий, но достаточный контекст (сам PID + соседние PID); (б) изменение
  контракта evaluator'а — затронет тесты и адаптеры; (в) риск пропуска
  меж-chunk-контекстных находок, которые ловит полный chunk-аудит. Митигация:
  оставить полный chunk-аудит только в первичном Step 6, re-audit — per-PID.

### 3.2 Бачтить repair по chunk (все регионы chunk в одном вызове)

- Суть: по образцу B12 re-gate batching — один `repair_caller` на chunk со всеми его
  регионами/findings в одном запросе, разбор вердиктов по регионам из ответа.
  `_apply_region_edit` переиспользовать для per-region парсинга, транспорт — батч.
- Оценка экономии: ~55–60 вызовов/главу (75 → ~16–20).
- Риски: низкие — паттерн уже реализован и протестирован для re-gate (B12);
  нужен backward-compatible путь (caller без `batch` → per-region, как в B12).

### 3.3 Остановка re-audit по сходимости

- Суть: после round 1 сравнивать набор findings до/после ремонта (по `content_hash`);
  если блокирующих findings не прибавилось / набор не изменился — не гонять round 2
  re-audit и не запускать quarantined-retry re-audit по тому же scope. Детерминированный
  признак «нет прогресса» (0 новых blocking findings) — ранний выход.
- Оценка экономии: ~30–60 вызовов/главу (зависит от числа раундов).
- Риски: низкие; но требует аккуратного определения «изменение набора findings»
  (порядок/канонизация уже есть — `content_hash`), и не должен ломать resume-семантику.

### 3.4 (не рекомендуется сейчас) gemma_russian_review не на каждом chunk

- Суть: первичный аудит gemma_russian_review на каждом из 16 chunk'ов (16 вызовов).
- Не предлагаем: это политика качества, изменение рискованное; оставить до данных
  сравнения качества (см. план §6a — локальный прогон).

## 6. Открытые вопросы для ревью

1. Корректен ли вывод, что ~103 из 269 вызовов — re-audit целых chunk'ов? (проверка
   по фазам: 135 аудит − 32 первичный = ~103; события reaudit 54×2 детектора ≈ 108).
2. Достаточен ли узкий контекст (PID + соседние PID) для qwen/gemma re-audit, или
   обязателен весь chunk (семантика связности)? Если обязателен — предложение 3.1
   сводится к «не перепроверять неизменённые chunk'и», экономия меньше (~30–40).
3. Батч-ремонт по chunk (3.2): риск деградации качества ремонта при одном большом
   запросе на chunk (против per-region)? Есть ли прецеденты/тесты B12 для репорта?
4. Правилен ли признак сходимости (3.3): «набор blocking findings не изменился
   между раундами»? Не ломает ли это случай, когда findings те же, но текст исправлен
   (тогда re-audit нужен, чтобы подтвердить закрытие)?
5. Оценка экономии 45–55% — реалистична ли с учётом того, что часть re-audit вызовов
   может быть дешёвой (маленький input)? Стоит ли считать экономию по COST, а не по
   числу вызовов?
