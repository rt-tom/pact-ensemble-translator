# V4 Measurement Task B — model lifecycle / reload cost

Backing spec: `docs/plans/V4_SINGLE_RESIDENT_DRIVER_ARCHITECTURE_RU.md`
(измерительная задача 2 в § "Что измерить до кода"; см. также § "Подсчёт
перезапусков: 10 high-risk chunk'ов" для того, какую последовательность
переключений это должно объяснять числами вместо догадки).

Это измерение и есть тот "отдельный короткий `Gemma → Qwen → Gemma`
benchmark без production pipeline", который тот же документ прямо называет
недостающим (§ "Как использовать текущий двухфазный sequential run",
последний абзац).

## Зачем это отдельно от карточки А

Карточка А измеряет *насколько часто* разошёлся бы left-context. Эта
карточка измеряет *насколько дорого* каждое такое расхождение стоит в
реальном restart'е — то есть даёт число для правой стороны выбора
strict-vs-batch-first. Без него утверждение "20 restart — слишком дорого"
остаётся декларацией, а не решением (документ прямо это запрещает).

## Новая переменная: два билда llama.cpp (Vulkan / SYCL)

У вас сейчас параллельно два билда backend'а. Это не мешает задаче, а
добавляет к ней ось сравнения — но с одним жёстким правилом: **backend —
часть identity одного измерительного прогона, а не что-то, что можно
незаметно поменять внутри одной серии замеров.** Один прогон = один backend
(либо Vulkan, либо SYCL), все остальные условия (файлы моделей,
quantization, context-size, server flags, содержимое prompt) идентичны
между прогонами. Сравнение двух backend'ов — это два независимых
измерительных record'а, сопоставленных постфактум, не один смешанный.

Это стоит сделать раньше остального: если один backend даёт заметно
дешёвый reload на этом железе, это меняет вес аргумента "20 restart
недопустимо дорого" и может вернуть строгий stop-and-switch в кандидаты на
default без approximation batch-first вообще — то есть результат этой
карточки может сам по себе повлиять на то, нужна ли карточка "Е"
(non-inferiority сравнение) в принципе, или strict можно принять сразу по
цене.

## Roles / boundaries

- **Не production pipeline.** Никакой реальной главы, никакого
  `pact_translate_v3`/v4 driver'а. Синтетический фиксированный prompt
  достаточен — это замер тайминга lifecycle, не качества перевода.
- **Lifecycle adapter управляет только тем, что сам запустил.** Не
  подключаться к чужому уже работающему `llama-server` и не останавливать
  его — тот же инвариант, что и в разделе "Model lifecycle" архитектурной
  записки.
- **HTTP success — не доказательство освобождения VRAM.** Освобождение
  памяти после `stop`/unload подтверждается наблюдаемым runtime state
  (напр. `nvidia-smi`/аналог для используемого backend'а), а не просто тем,
  что процесс завершился или HTTP-соединение закрылось.
- Результат — новый versioned measurement record, не изменение
  production-конфигурации и не выбор default backend'а этой же карточкой.

## Что мерить

Полная последовательность `G → Q → G → Q → …`, а не одиночный
`Gemma → Qwen` swap (одиночный swap — это только один sample, сам документ
явно предупреждает не путать его с оценкой деградации от серии restart).
Число чередований — зафиксировать заранее (напр. 10, по аналогии со
сценарием "10 high-risk chunk'ов" из сравнения вариантов), не подгонять по
факту.

На каждое переключение:

- `cold_acquire_seconds` — от старта процесса до готовности endpoint'а
  (health/first successful completion);
- `unload_seconds` — от команды stop/release до подтверждённого
  освобождения VRAM (не до просто exit процесса);
- `first_token_seconds` и `completion_seconds` для одного фиксированного
  synthetic-запроса на роль (Gemma generation-подобный, Qwen gate-подобный,
  Gemma preference-подобный — разные по форме, чтобы не мерить одно и то же
  дважды под разными именами);
- `peak_vram_mb` за время, пока сервис держит модель;
- `errors` — любые сбои старта/остановки/таймауты, с текстом причины, не
  молча пропускаемые.

Агрегаты по всей серии: суммарный `wall_clock_seconds`, число успешных
переключений, число ошибок, per-role медиана/p95 по каждому из полей выше.

## Procedure (эскиз, без готового кода — сама карточка не запускает бенчмарк)

1. Выбрать один backend build (Vulkan **или** SYCL) на прогон, зафиксировать
   его в provenance записи (build id/commit/flags запуска `llama-server`).
2. Запустить Gemma, дождаться готовности, выполнить один фиксированный
   synthetic completion, записать `cold_acquire`/`first_token`/`completion`.
3. Остановить Gemma, подтвердить освобождение VRAM внешним наблюдением,
   записать `unload_seconds`.
4. Запустить Qwen, повторить п.2 для Qwen-подобного запроса.
5. Остановить Qwen тем же образом.
6. Повторить цикл `Gemma ⇄ Qwen` N раз (зафиксированное число), не
   прерывая на середине без записи причины прерывания.
7. Повторить весь прогон отдельно для второго backend'а, если оба билда
   тестируются, как независимый record, не как правку первого.

## Acceptance

- Два (или один, если тестируется только один backend в этот раз) отдельных
  versioned measurement record'а с полями выше, каждый с backend/build
  identity, model files, quantization, context-size, server flags и числом
  переключений в provenance.
- Ни один запуск не подключается к чужому `llama-server` и не работает
  поверх production конфигурации/артефактов.
- Нет изменений в `pact_v4/`, нет запуска реального перевода главы.
- Явно отмечено (в тексте record'а), если серия прервалась раньше
  зафиксированного N — с причиной, не тихим усечением таблицы.
