# Доработки для устойчивости whole-chapter generation — рекомендации
**Источник:** анализ прогона `v4-1-0022-0025-local-20260818-1`, chapter `0025_collateral-4-2` (FAILED)
**Дата:** 2026-08-18/19
**Статус:** предложения (backlog) — ждут решения владельца; НЕ реализованы.

## Контекст / симптомы
Как прогон отчёт в `book_run.json`:
- `0025_collateral-4-2`: `skipped (not promoted) [FAILED]`, `incomplete_generation=1`, `halted_early=True`,
  `step6=skipped step7=skipped terminal=skipped`, `wall_clock=2953.2s`, `restarts=1`.
- Причина отказа: `PID set mismatch` на все 3 попытки whole-chapter generation (строгий exact-PID контракт).

Фактура по attempt-файлам:

| attempt | PID-ключей / 331 | покрытие | мусорный ключ | JSON |
|---|---|---|---|---|
| 0 | 330/331 | весь текст (p00001–p00331) | `}}>```json`` | валиден |
| 1 | 158/331 | обрывается на p00158 | нет | валиден |
| 2 | 158/331 | обрывается на p00158 | ` — начал пьяница. ` | валиден |

Ключевой факт: это **НЕ truncation** — server_logs: `stop processing: n_tokens = 29603, truncated = 0`, `finish_reason = stop`.
Модель (generator = `gemma-4-26B`, `model_bindings.generator`) **добровольно сошла на stop-символ на середине главы**,
оставив ~170 PID (p00159–p00331) непокрытыми. Контекст (49152) и `max_tokens` (32768) не исчерпаны.

Паттерн: attempt 0 почти весь (330/331, один missing → retry); на ретраях Gemma фокусируется на начале главы
(огромный reasoning-план 6000+ символов, детально на первые ~p00100) и стабильно бросает вывод на p00158
(середина 331), плюс под конец утекает dialogue-attribution как ключ (` — начал пьяница. `).

Вывод: **проблема устойчивости/поведения Gemma (local_llama) на длинных whole-chapter генерациях**, а не железо,
не контекст и не регрессия chain-кода (строгий exact-PID контракт сработал корректно и защитил от проталкивания
усечённого перевода).

## Рекомендации (по приоритету)

### 1. (Самый надёжный) Whole-chapter с safety fallback на partial — «приличный деградированный результат вместо fail»
Строгий контракт требует все 331 PID или fail — для длинных глав это делает одиночную Gemma-генерацию хрупкой.
- Если после N retries нет полного совпадения, но есть **стабильное согласованное подмножество** (напр. в 2 из 3 попыток
  покрыты p00001–p00158 с пересечением ключей), разрешить `promote` как `accepted_degraded` (не `skipped`),
  пометив недостающие PID как «нуждаются в отдельном дозаполнении». Механизм `accepted_degraded` уже существует
  (chapter 0023) — это расширение той же логики.
- Недостающие PID затем договариваются **отдельным целевым вызовом переводчика по списку отсутствующих ключей**
  (а не перегенерацией всей главы).

### 2. Специализировать ретрай-подсказку на «продолжи с pXXXX»
Ретрай сейчас, видимо, подаёт полный план/главу заново → Gemma снова стартует с начала и бросает на середине.
- На retry#2/#3 явно инструктировать: *«перевод уже покрыт до p00158 — выведи только недостающие p00159…p00331»*,
  класть в контекст только недостающую часть. Экономит токены и не даёт модели «рестартовать» раскладку.

### 3. Усилить контракт по структуре JSON до разбора (transport-шум)
Мусорные ключи `— начал пьяница.` и `}}>`json`` показывают, что модель вставляет посторонний ключ/обрамление.
- Разрешать/игнорировать известные расчётные ключи (`pid_count`, `candidates`, …) при подсчёте mismatch так, чтобы
  единичный посторонний ключ не ронял всю попытку.
- Либо детектировать и автоматически чистить только transport-шум (markdown fences, `}}>`json``) как не-перевод.
- Диалоговый текст как ключ — сигнал «протекания» атрибуции реплик; в промпт добавить жёсткое: «ключи могут быть ТОЛЬКО pXXXXX».

### 4. (Инфра) Ранний отказ «по доле токенов» → сразу дозаполнение
Доступен `n_decoded` (usage/server_logs). Для главы 331 PID вызов, который останавливается на ~47% (158/331) при
`finish_reason=stop`, — сигнатура. Доработка: если `n_decoded << ожидания` и `finish_reason=stop`, сразу переходить на
стратегию «дозаполнение недостающих PID» (п.2), а не жечь ещё один полный ретрай в ту же середину.

### 5. Мониторинг инфекции «половина главы»
Добавить в монитор/`book_run.json` тип отказа `whole_chapter_half_stop`
(сигнатура: missing-PID диапазон начинается ≈с середины + finish_reason=stop + truncated=0).
Автоматизирует диагноз и подсвечивает, что Gemma системно сбоит на long-gen — видно в итоговой таблице.
