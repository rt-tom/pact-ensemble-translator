# Две локальные модели на отдельных устройствах: предложения для book-пайплайна

Дата: 2026-09-07. Основание: обсуждение с владельцем и код `main` на
`cf106359fb9ee2c4a33ec5d841776852e547e24a`.

**Статус: план вариантов и экспериментов, без реализации.** Публикация этого
документа не утверждает изменение runtime, моделей, промптов, форматов данных
или production-политики. Ниже нет результатов производительных замеров и
подтверждённого прироста качества.

## 1. Условия и цель

Владелец подтвердил: каждую из двух моделей можно держать на отдельном устройстве.
Это позволяет перекрывать вычисления, а не только экономить на перезагрузке весов.
Общие CPU, RAM, ввод-вывод и транспорт всё равно могут создавать конкуренцию;
независимость ускорителей сама по себе не гарантирует двукратного ускорения.

Рабочее разделение ролей:

- **Переводчик:** русский литературный текст, адресные исправления; возможно,
  русская редактура и альтернативные формулировки.
- **Аналитик/аудитор:** понимание оригинала, сущности, смысловые ограничения,
  проверка предложенных изменений и повторный аудит.

Владелец предполагает заменить Qwen на Qwen 3.8 и ожидает сильный анализ при менее
сильном переводе. Это **предпосылка владельца, не проверенная здесь характеристика
модели**; выбор версии и назначения ролей требует отдельного сравнения.

Цель — сократить время до готового проверенного результата и уменьшить смысловые
ошибки, сохраняя fidelity, причинную последовательность памяти книги, полноту
аудита и корректность resume. Загрузка двух устройств на 100% не является целью.

## 2. Фактическая отправная точка

Основной обзор:
[инвентаризация book-пайплайна](../architecture/V4_BOOK_PIPELINE_INVENTORY_RU.md).
При расхождениях приоритет у кода соответствующей ревизии; инвентаризация и данный
план не являются свидетельством фактического состояния запущенных серверов.

Обычный `book` принудительно использует whole-chapter генерацию, а не исторический
chunked A/B-selection путь. Упрощённая последовательность:

```text
source snapshot и PID → entity prepass → перевод всей главы
→ RU-редактор → полный исходный B3-аудит → hard filters
→ selective repair → re-audit → inline formatting → обновление памяти
→ следующая глава
```

Здесь «полный исходный аудит» означает завершение предусмотренных проверок главы
перед ремонтом; отдельные запросы аудита могут быть chunked.

Ключевые ограничения и точки входа:

| Факт | Опора в коде |
|---|---|
| Главы проходят book-оркестратор последовательно; контекст следующей главы зависит от принятой памяти предыдущей | [v4_book_run.py](../../pact_full_pipeline_runner_v1/v4_book_run.py) |
| Entity prepass уже независимо читает оригинал до перевода; это основа для расширения, а не отсутствующая функция | [entity_extractor.py](../../pact_v4/audit/entity_extractor.py), [B3-интеграция](../../pact_v4/pipeline/b3_audit_repair.py) |
| Локальный ModelRouter переключает активную модель с остановкой предыдущей | [model_lifecycle.py](../../pact_v4/runtime/model_lifecycle.py) |
| Есть composite runtime и маршрутизация по backend; пригодность для постоянной пары надо проверить, она не означает готового параллельного book-конвейера | [runtime_config.py](../../pact_v4/runtime/runtime_config.py), [runtime_coordinator.py](../../pact_v4/runtime/runtime_coordinator.py) |
| RU-редактор получает русский текст без оригинала; SAFE-правки применяются, REVIEW остаются кандидатами для проверки repair-as-verifier | [russian_editor.py](../../pact_v4/audit/russian_editor.py) |
| Редактор и аудитор сейчас используют audit backend; перевод и ремонт — generator | [B3-интеграция](../../pact_v4/pipeline/b3_audit_repair.py), [локальный профиль](../../configs/runtime_local.example.yaml) |
| Перед ремонтом замечания по одному PID объединяются, затем выполняется один проход ремонта и re-audit | [selective_repair.py](../../pact_v4/repair/selective_repair.py) |
| Ошибка выполнения re-audit сбрасывает repair_complete; остаточные findings добавляются в debt и сами по себе не сбрасывают этот флаг | [selective_repair.py](../../pact_v4/repair/selective_repair.py) |
| Inline formatting запускается book wrapper и использует переводческую роль | [v4_book_run.py](../../pact_full_pipeline_runner_v1/v4_book_run.py), [formatting.py](../../pact_v4/phase5/formatting.py) |

`repair_complete` нельзя интерпретировать как отсутствие всех ошибок. Предложение
дополнительного ремонта ниже не меняет этот контракт автоматически.

## 3. Постоянная пара моделей на весь book-run

**Первый инфраструктурный приоритет:** сохранить оба backend доступными на всём
протяжении книги, включая переходы между главами, ремонт и финальное форматирование.
Сохранение пары только внутри одной главы оставляет часть стоимости пересоздания
runtime и переключений.

Начать следует с двух загруженных моделей при прежнем последовательном порядке
вызовов. Это изолирует выигрыш от устранения загрузок от эффекта параллелизма и не
приписывает ускорению изменение качества.

Проверить composite runtime как существующую основу: явные назначения ролей,
однозначность model_ref, владение серверами, readiness, обработку отказа одного
backend и завершение book scope. Нужна согласованная политика для собственных и
внешних серверов; агент не получает права останавливать чужие процессы.

Область будущих изменений: runtime config/coordinator/lifecycle, создание и
передача runtime в strict runner и book wrapper. Это High risk из-за lifecycle,
routing и обработки отказов, даже если итоговый текст должен остаться прежним.

Две резидентные модели не равнозначны speculative decoding. Произвольная пара
«переводчик + аналитик» не становится draft/target парой автоматически. В текущем
локальном профиле уже есть настройка `draft-mtp`; ускорение декодирования следует
измерять отдельно и не засчитывать повторно как эффект предлагаемой архитектуры.
Увеличение числа слотов запросов сервера также не заменяет зависимостей и
планировщика book-пайплайна.

## 4. Entity prepass на одну главу вперёд

**Первый параллельный шаг для скорости:** пока переводчик генерирует главу N,
аналитик извлекает сущности из оригинала N+1.

Условия корректности:

- Заранее вычисляется только результат, зависящий от исходника. Полный промпт
  перевода и snapshot памяти для N+1 фиксируются после принятия главы N.
- Результат подготовки привязан к конкретным исходнику, PID-карте, версии
  extractor/контракта и настройкам модели. Совпадения номера главы недостаточно
  для повторного использования.
- Факты N+1 не попадают в промпт, память или аудит главы N. Future context не
  должен менять то, что перевод текущей главы вправе знать.
- Предел опережения первой версии — одна глава. Ошибку фоновой подготовки
  фиксировать явно; необходимый prepass можно выполнить штатно перед переводом.
- Фоновая очередь уступает обязательной проверке текущей главы. Ограничивать
  размер заданий нужно до запуска: уже идущий длинный inference может не иметь
  дешёвого прерывания.

При независимых вычислениях идеальная экономия на переходе ограничена
`min(время генерации N, время prepass N+1)`, за вычетом накладных расходов.
Первой главе всё равно нужна подготовка. Это оценка перекрытия, не измеренный
выигрыш всего прогона. Дополнительных вызовов для самого entity prepass не нужно.

## 5. Расширенный независимый анализ оригинала

**Главная гипотеза качества:** дать переводчику компактную информацию о трудных
местах до генерации, чтобы снизить вероятность ошибок понимания.

Entity extractor уже решает часть задачи. Не нужен второй независимый перечень
тех же персонажей. Предлагается дополнить source-анализ картой проверяемых
смысловых ограничений:

| Содержание подсказки | Какие ошибки она помогает предупреждать |
|---|---|
| Говорящий, адресат, референты местоимений с обозначением неопределённости | Перепутанные реплики, род и обращения |
| Субъект и объект действия, порядок событий, причинная связь | Перестановка участников и причинности |
| Отрицание, условие, сомнение, степень уверенности | Превращение предположения в факт |
| Знание персонажа и знание рассказчика | Приписывание персонажу недоступной информации |
| Идиома, переносное значение, намеренная двусмысленность | Буквализм и необоснованное устранение неоднозначности |
| Ирония, грубость, недосказанность, значимый повтор и смена регистра | Стилистическое сглаживание, меняющее смысл |

Формат — краткий вывод, PID или диапазон PID, привязка к свидетельству в оригинале
и явная неопределённость. Это не длинная цепочка рассуждений и не пересказ главы.
Точное происхождение свидетельства не доказывает верность интерпретации.
Переводчик продолжает получать полный оригинал; подсказки не вправе его
переопределять и не являются автоматическими командами на переписывание.

Первая реализация может расширить результат существующего prepass отдельным
семантическим разделом, сохранив контракт проверки сущностей. Если объединённый
запрос ухудшит extraction, полноту или стоимость, разделить вызовы. Предусмотреть
ограничение числа подсказок и приоритет действительно сложных мест.

### Когда готовить анализ

Для влияния на перевод N анализ должен завершиться **до генерации N**. Поэтому
предпочтителен анализ N+1 во время перевода N, с последующим сопоставлением
подсказок с принятой памятью. Русские имена, принятые обращения и другие
memory-dependent решения нельзя окончательно фиксировать на устаревшей памяти.

Source-only часть и результат согласования с memory должны иметь разные
зависимости. Изменение памяти требует нового согласования, а изменение исходника
может инвалидировать обе части. Аналитические гипотезы не записываются
автоматически в persistent glossary/book memory.

Если аналитик читает оригинал N одновременно с уже начавшимся переводом N, это
**разведка для последующего аудита**, а не помощь данной генерации. Такой режим
тоже полезен как отдельный эксперимент, но эти эффекты нельзя смешивать.

### Как проверять пользу

Начать с наблюдательного режима: сохранять карту, но не менять перевод или
обязательный аудит. В отдельной человеческой оценке сопоставить карту с готовым
переводом и оригиналом; сами пункты карты не считать findings. Затем сравнить
перевод с подсказками и без них при прежних параметрах.

Если тот же аналитик использует собственную карту в аудите, появляется риск
подтверждения собственной ошибки. Полный аудит по оригиналу сохраняется;
подсказка не служит доказательством finding. Отдельно оценивать ложные подсказки,
их принятие переводчиком и случаи, когда они ухудшили текст.

Сокращение reasoning-бюджета переводчика — **следующий самостоятельный
эксперимент**, после подтверждения пользы подсказок. Предположение «меньше
неопределённости — меньше рассуждений» правдоподобно, но дополнительный контекст
может увеличить стоимость prefill и не сократить generation.

## 6. Независимые альтернативы только трудных фрагментов

Вместо полного двойного перевода каждой главы получать второй вариант для мест,
где карта рисков, аудит или неудачный ремонт показывают неоднозначность: референты,
сложная причинность, идиомы, игра слов, подозрительно гладкая потеря смысла.

Сначала модель получает оригинал и необходимый допустимый контекст **без первого
русского варианта**. Затем варианты сравниваются по исходнику. Расхождение само
по себе не означает ошибку, а благозвучие не является достаточным критерием выбора.

При предполагаемой слабости Qwen в переводе полезнее сначала запросить независимую
трактовку смысла. Генерацию полноценной русской альтернативы поручать ему только
если отдельная оценка это оправдала; альтернативу может создавать переводчик
новым изолированным запросом. Последний вариант не даёт независимости моделей
и занимает его устройство — это нужно учитывать в сравнении.

Ограничивать число фрагментов, размер контекста и дополнительный бюджет. Обычные
места идут штатным путём. Полный A/B whole-chapter перевод остаётся отдельным
дорогим экспериментом с новой задачей выбора, не первым шагом.

## 7. Проверка редакторских предложений по мере готовности

Идея имеет смысл прежде всего как **проверка конкретного изменения**. Аудитор
получает оригинал, русский текст до правки, предложение, причину и необходимый
контекст; оценивает два вопроса:

1. Существует ли проблема в прежнем тексте?
2. Устраняет ли её предложение, не внося потери смысла или новых ошибок?

Вредное предложение отклоняется с сохранением прежнего текста. Новый ремонт
нужен, только если подтверждённая проблема действительно остаётся. Это уменьшает
число ненужных переписываний.

Текущий SAFE auto-apply и REVIEW repair-as-verifier — исходные контракты.
Проверка всех SAFE до применения будет их изменением; её нельзя выдавать за
существующее поведение или незаметно включить вместе с параллелизмом.

Практическая единица — небольшая группа правок по связному фрагменту, а не один
вызов на каждую запятую. Нужны актуальная версия исходного русского текста,
контроль принадлежности PID и повторная валидация перед применением. Проверка
кандидатов дополняет полный аудит главы, а не заменяет его.

Редактор и аудитор сейчас используют Qwen. Чередование двух запросов на одном
backend даёт раннюю обратную связь, но не перекрытие работы на двух устройствах.
Отдельный эксперимент — перенести RU-редактуру на переводческую модель:
переводчик предлагает русский текст, аналитик независимо сверяет смысл.
При этом редактура конкурирует на первом устройстве с ремонтом, альтернативами
и форматированием. Результат сравнивать с прежней редактурой, а не считать
перенос заведомо лучшим.

## 8. Почему не стоит немедленно ремонтировать каждую находку

В selective repair уже объединяются все замечания по одному PID. Код фиксирует
важный мотив: последующая стилистическая правка могла отменить более раннее
исправление fidelity.

Поэтому в первой версии:

- Ранняя проверка принимает или отклоняет редакторские предложения.
- Подтверждённые остаточные проблемы собираются вместе с замечаниями аудитора.
- До ремонта сохраняется барьер завершения полного исходного аудита.
- Ремонт получает объединённые замечания по PID и достаточный связный контекст.
- Полнота, hard filters, eligibility и существующие лимиты не обходятся ради
  скорости.

Это даёт пользу от ранней проверки без нового цикла конкурентного переписывания.
Ослабление исходного барьера — отдельное архитектурное решение, не часть первого
предложения.

## 9. Один дополнительный адресный раунд ремонта

Сейчас остаточные findings после re-audit попадают в debt без следующего прохода.
Предложение — разрешить **не более одного дополнительного адресного раунда**,
то есть максимум два прохода ремонта, и затем снова проверить результат.

Во второй раунд входят подтверждённые остаточные или внесённые предыдущим
ремонтом ошибки, прошедшие применимые фильтры и ограничения. Сам факт появления
finding не даёт автоматического права на переписывание.

Переводчик получает исходник, актуальный контекст, варианты до и после предыдущей
попытки и конкретное объяснение оставшейся ошибки. Все замечания к области снова
объединяются. Нужна история версий и результатов проверок, чтобы отличать новую
попытку от воспроизведения отклонённого текста.

Условия остановки:

- проблема устранена по успешной проверке;
- достигнут лимит дополнительного раунда или модельного бюджета;
- повторяется уже отклонённый вариант либо нет содержательного изменения;
- проверка не завершилась корректно или недостаточно доказательств для
  безопасного исправления.

После изменения повторно проверять затронутый текст и его зависимости. При
остановке сохранять явные debt/diagnostics, не объявлять отсутствие проблем по
одному `repair_complete`. Не вводить цикл «пока модели не согласятся».
Точные критерии допуска, приоритеты ошибок и лимиты должны быть утверждены в
OpenSpec, а не возникать как скрытая новая продуктовая политика.

## 10. Продвинутый конвейер «ремонт → re-audit»

После завершения исходного аудита переводчик исправляет область A; аналитик
проверяет готовую A, пока переводчик исправляет независимую B. Потенциал выше
на главах с большим объёмом подтверждённых исправлений.

Разные целевые PID ещё не означают независимость. Read-set проверки включает
все входные тексты, соседние PID, память, source snapshot и другие влияющие
данные. Если B меняет контекст, использованный при проверке A, проверка A
становится устаревшей.

Необходимые свойства будущего дизайна:

- неизменяемые снимки запросов и идентификаторы версий от оркестратора;
- явные read-set/write-set для операций;
- применение результата только к ожидаемой версии, без last-writer-wins;
- инвалидация и повторная проверка при изменении зависимостей;
- детерминированное объединение результатов, корректный journal/resume;
- отказ проверки не превращается в пустой успешный результат;
- финальный барьер полноты перед выпуском результата.

Это High risk и поздний этап. Параллелизм стоит вводить после измерения
стоимости ремонта и проверки эффективности дополнительного адресного раунда.

## 11. Предварительное inline formatting во время аудита

Пока аналитик проверяет отредактированный текст, переводчик может заранее
вычислить сопоставление inline spans. После ремонта оставить только результаты,
чьи входные зависимости не изменились, остальные пересчитать.

Валидировать нужно **весь read-set запроса**, а не только целевой PID: изменение
соседнего контекста тоже делает результат потенциально устаревшим. Теги применять
к финальному принятому тексту после проверки полноты.

Здесь speculative означает предварительное вычисление с возможным отбрасыванием,
а не speculative decoding. Польза зависит от плотности разметки; при редких
выделениях выигрыш может не окупить сложность и повторные вызовы. Задача
конкурирует с редактурой и адресным ремонтом на переводческом устройстве.

## 12. Планирование и режимы

Базовое расписание после инфраструктурного шага:

| Интервал | Устройство переводчика | Устройство аналитика |
|---|---|---|
| Старт книги | Ожидание необходимой подготовки | Entity prepass и выбранный source-анализ первой главы |
| Генерация N | Перевод N | Source-only подготовка N+1; в отдельном режиме — независимая разведка для аудита N |
| Редактура и исходный аудит N | Возможная RU-редактура в эксперименте | Штатная редактура, затем аудит; либо проверка предложений редактора |
| Ремонт N | Исправление подтверждённых проблем | Проверка готовых областей только при доказанной независимости |
| Завершение N | Форматирование | Обязательные завершающие проверки |
| Переход | Перевод N+1 после фиксации актуальной памяти | Следующая подготовка |

Это набор совместимых направлений, а не утверждение, что все фоновые работы
умещаются одновременно. Обязательные проверки текущей главы имеют приоритет.

Два режима поверх общей инфраструктуры:

- **Скорость:** постоянная пара, prepass на главу вперёд, минимальный
  дополнительный анализ; позднее — оправданное замерами перекрытие ремонта.
- **Качество:** расширенная подготовка до перевода, проверка редакторского diff,
  адресные альтернативы и один дополнительный ремонт по подтверждённым ошибкам.

Для режима качества увеличение времени допустимо только как явный измеренный
компромисс. Нельзя считать занятость устройств, число findings или количество
правок самостоятельными показателями качества.

Перевод соседних глав одновременно не предлагается: он затрагивает причинную
память, согласованность сущностей и повторное использование результатов.
Полный двойной перевод каждой главы также не является стандартным режимом.

## 13. Как сравнивать варианты

Все прогоны — отдельные эксперименты после разрешения владельца; production
pipeline по-прежнему запускает владелец вручную. Этот документ не запускает
эксперименты и не разрешает использование чужих данных или внешних сервисов.

Последовательность сравнений:

1. Текущий baseline.
2. Две постоянно загруженные модели при прежнем порядке вызовов.
3. Та же пара с опережающим entity prepass.
4. Расширенный анализ: сначала наблюдение, затем подсказки переводчику.
5. Один дополнительный адресный ремонт.
6. Проверка редакторского diff; отдельно — перенос редактора на переводчика.
7. Адресные альтернативы, конвейер ремонта и предварительное форматирование
   только там, где предыдущие замеры показывают смысл.
8. Уменьшение reasoning-бюджета — отдельная вариация после фиксации эффекта
   подсказок.

Для каждого сравнения фиксировать одинаковые identity исходников и PID, входной
памяти, glossary, кода, конфигурации, квантования, контекстного окна и прочих
параметров, кроме исследуемого фактора. В сценариях полного book-run память
может расходиться вследствие разных переводов: это отдельный эффект, который
нужно учитывать, а не маскировать как matched-state сравнение.

Разделять cold и warm runs, учитывать загрузку моделей и повторное использование
артефактов. Нельзя сравнивать холодный baseline с прогоном, где значительная часть
работы взята из cache. Использовать несколько сопоставимых глав и повторения;
сложные и типовые фрагменты оценивать раздельно.

**Скорость:** end-to-end время до проверенного оформленного результата, время
каждой стадии, ожидание очереди, загрузки, prefill/generation, количество вызовов
и токенов, повторные проверки и отброшенные предварительные результаты.
Tokens/s одной модели не описывает скорость книги.

**Качество:** подтверждённые смысловые ошибки, пропуски и добавления, сущности,
обращения, модальность, художественно значимые особенности, ложные findings,
неверные подсказки и новые ошибки от редактора/ремонта. Отдельно считать остаточный
debt, сбои и неполные проверки.

Нужна слепая человеческая оценка по оригиналу хотя бы на сопоставимой выборке.
Согласие того же аналитика со своей подсказкой и увеличение числа исправлений
не доказывают улучшение fidelity. Критерии успеха и допустимый компромисс
время/качество согласовать до эксперимента, не подбирать после результатов.

## 14. Приоритеты, области реализации и границы согласования

| Шаг | Основная польза | Сложность / риск будущей реализации |
|---|---|---|
| Постоянная пара на книгу | Убрать загрузки, создать основу параллелизма | Средняя сложность, High: lifecycle/routing |
| Prepass на главу вперёд | Скрыть существующую подготовку за генерацией | Средняя сложность, High: orchestration/resume |
| Расширенный source-анализ | Предупреждать ошибки понимания | Medium для изолированного эксперимента; High при новых артефактах/resume |
| Дополнительный адресный ремонт | Исправлять часть текущего residual debt | High: orchestration/status/provenance |
| Проверка редакторских предложений | Отсекать вредные изменения, объяснять пользу правки | Medium для изолированного эксперимента; High для конвейера |
| Альтернативы сложных фрагментов | Дополнительная независимая трактовка | Средняя–высокая сложность, требуется оценка качества |
| Перекрытие ремонта и re-audit | Ускорить главы с большим ремонтом | Высокая сложность, High |
| Предварительное форматирование | Скрыть часть завершающего этапа | Средняя сложность, High при изменении orchestration/resume |

Основные области кода: runtime lifecycle/config/coordinator; book wrapper и
[strict runner](../../pact_full_pipeline_runner_v1/v4_phase12_strict_run.py);
entity extractor и [B3](../../pact_v4/pipeline/b3_audit_repair.py); RU-редактор;
selective repair; formatting. Изменения промптов, hard filters и memory contracts
должны быть явно названы в соответствующем предложении, а не добавлены попутно.

Рекомендуемый порядок: инфраструктура и prepass → расширенный анализ →
ограниченный дополнительный ремонт → редакторский diff → более сложный
параллелизм. Наблюдательное исследование качества можно спроектировать до
полного конвейера, если оно не меняет production state.

Для существенных изменений нужны отдельные утверждённые OpenSpec proposal,
design, tasks и критерии приёмки. При новых persistent форматах заранее описать
совместимость, миграцию и откат. Отказ от эксперимента должен позволять вернуться
к baseline без перезаписи production артефактов.

Сам этот файл — Low-risk документация. Его commit/push в main не является
разрешением на реализацию предложений, смену модели, деплой, изменение серверов,
миграцию данных или запуск pipeline.
