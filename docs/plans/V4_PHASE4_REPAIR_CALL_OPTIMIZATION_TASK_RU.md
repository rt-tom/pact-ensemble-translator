# V4 Phase 4 — оптимизация вызовов моделей в фазе ремонта (карточка)

Backing: решение владельца и записи `DECISIONS.md` от 2026-08-03 (L1/L2b/L3);
текущая реализация Phase 4 (`pact_v4/phase4/repair.py`, Step 7/8 в
`pact_v4/pipeline/v4_phase12_strict_runner.py`, B2).

## Зачем

Live-прогон главы 0001 (`D:\pact\gate_bench_runs\v4_phase12_strict_0001\run_001`,
strict driver, local_llama) показал: фаза ремонта (Step 7) стоит в раунде 1
**~310 модельных вызовов и ~190 переключений моделей** на 95 регионов. Доминирует
Qwen re-gate по **всему чанку** (~3 мин / ~5200 токенов на регион), который затем
дублируется convergence re-audit тех же чанков теми же моделями. Задача — сократить
число вызовов и переключений, сохранив качественную логику ремонта.

## Инварианты, которые нельзя нарушать

1. **Минимальный region-ремонт** (CREAMT / литературный обзор, п.3): `region_edit`
   по умолчанию; `full_sentence_rewrite` — только в раунде 2 с documented reason.
2. **Независимый семантический верификатор ≠ модель-редактор** (дефект v3: Gemma
   переводила и сама ревьюила, DECISIONS 2026-08-01). Регейт остаётся на Qwen,
   редактор — на Gemma. Предел — две модели; роли уже максимально разделены
   (Gemma = редактор + русский речек; Qwen = регейт + re-audit).
3. **Двухмодельная проверка правки**: Qwen (семантика) + Gemma (русский;
   обязателен для регионов, закрывающих Gemma-финдинг, после прохождения гейтов).
4. **Convergence re-audit** изменённых PID + дискурс-соседей с детерминированным
   слоем; transport failure = debt, не семантический терминальный статус;
   no silent fallback.
5. Терминальные `complete / accepted_degraded / failed` монотонны (write-once).

## Что реализовать

### 1. L1 — батчинг convergence re-audit по модели

`pact_v4/phase4/repair.py::_reaudit_chunks`: переставить цикл
`for chunk_id in chunk_ids: ... for detector, evaluator, allowed in (...):` на
`for detector, evaluator, allowed in (...): for chunk_id in chunk_ids:`.
Детерминированный слой остаётся per-chunk (без модели). Набор находок должен быть
тождествен независимо от порядка. Обоснование уже зафиксировано: DECISIONS
2026-08-01 (Phase 3: юниты независимы, батч по детектору даёт ~1–2 switch вместо
~2N). Нулевое семантическое изменение.

### 2. L2b — узкий per-регионный регейт + батчинг ролей в проходы

Реструктурировать раунды 1 и 2 (`run_repair_phase`, `repair_region`) с немедленной
последовательности «правка → регейт → речек» на проходы по ролям:

1. **Gemma pass (один lease):** все `region_edit` по всем спланированным регионам;
   правки применяются к `translation_by_chunk` как tentative.
2. **Qwen pass (один lease):** узкий регейт по каждому правленому региону — новый
   промпт-вариант `region_fidelity_gate` (только source PID + правленый текст +
   регион, короткий JSON-вердикт). Неправленые PID'ы покрывает re-audit.
3. **Gemma pass (один lease):** речеки для регионов, чей регейт прошёл и которые
   закрывают Gemma-финдинг (`_gemma_recheck_required`).
4. **Коммит** регионов, прошедших регейт (+ речек где требуется); неудачные —
   debt, находки остаются открытыми.
5. **Convergence re-audit** (батчированный, L1) по изменённым чанкам + соседям.

Требования:
- Критерии коммита не меняются (fidelity passed + gemma-recheck passed где
  требуется); меняется только скоуп регейта (правленый PID вместо всего чанка) и
  отложенность коммита (до конца прохода).
- `repair_id` и unit_hash кэша остаются стабильными; кэш-семантика (reuse только
  при полном совпадении identity, foreign-identity проверка) сохраняется.
- Новый промпт-вариант регейта — через Backend-адаптеры над coordinator
  `CompletionBackend` (без локальных lifecycle-адаптеров в repair-коде),
  узкий парсер вердикта на основе `_parse_qwen_verdict`.

### 3. L3 — severity-фильтр мягких Gemma-находок (по силе доказательства)

- Скоуп: soft-категории `calque`, `register` (опционально `repetition`) **только
  со слабым доказательством** — короткий excerpt (порог длины, напр. <60 символов)
  и/или неуверенная формулировка note («sounds like», «might be», «likely»).
  Уверенные находки остаются в ремонте.
- Точка внедрения: `plan_repairs_for_chunk` (или пре-фильтр перед ним). Находки
  **остаются в store** (append-only, `audit_findings.json`); фильтруется только
  планирование ремонта.
- **Критично:** soft-категории исключаются из определения blocking в раунде 2
  (иначе re-audit снова их поднимет и экономия исчезнет). Пропущенные soft-находки
  фиксируются в debt trace / `repair_report.json`.
- Пороги и правила — параметры (константы с документированной политикой или
  benchmark-config), не магия в коде.

## Acceptance criteria

1. **L1:** набор находок re-audit тождественен при обоих порядках циклов
   (fixture/unit-тест).
2. **L2b:** узкие регейт-вердикты совпадают с полными на fixture; набор коммитов
   при замороженных вердиктах моделей не меняется; `repair_id` и кэш-идентичность
   стабильны.
3. **L3:** unit-тесты фильтра (слабое/сильное доказательство); soft-находки не
   блокируют раунд 2; debt trace фиксирует пропущенные.
4. **Офлайн-реплей:** прогон нового ремонтного пайплайна на замороженных
   вердиктах артефактов главы 0001 (`audit_findings.json`, `b2_handoff.json`,
   `audit_cache.json`) — сравнить решения/коммиты с текущей реализацией.
5. `tests/pact_v4/` зелёные; новые тесты покрывают новый поток (проходы,
   батчинг re-audit, фильтр, отложенный коммит).
6. Записи в `DECISIONS.md` (L1/L2b/L3 и трейд-оффы) — в этом же коммите.
7. Без мержа/деплоя/запуска пайплайна; draft PR.

## Известные риски

- Потеря контекста соседних правок внутри чанка при батчинге правок (регионы на
  разных PID; межрегионные нарушения ловит re-audit). Трейд-офф фиксируется в
  DECISIONS.
- Коммит откладывается до конца прохода: семантика debt/round-2 остаётся прежней,
  но гранулярность записи меняется.
- L3: часть реальных calque не чинится автоматически (идёт в debt). В v4 нет более
  поздней полировочной фазы — это осознанная политика владельца, а не дыра.
